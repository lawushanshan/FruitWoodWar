# 城堡战争：果林大战 —— 架构设计

> 版本：v0.4 ｜ 日期：2026-08-18 ｜ 状态：后续实现基线
>
> 本文档定义代码边界和演进顺序，不替代玩法和数值设计。玩法规则以《01-玩法设计总纲》为准，数值以《02-数值设计表》为准，执行顺序以《03-开发落地路线图》为准。

## 1. 架构目标

当前工程是一个集中式灰盒原型：`GameManager.ts` 同时负责配置、游戏状态、模拟、AI、UI 和渲染。后续迭代必须先建立稳定的模拟核心，再逐步替换表现层。

架构目标：

1. 规则模拟不依赖 Cocos，能够在 Node/测试环境中独立运行。
2. UI 只发送命令、展示状态，不直接修改游戏数据。
3. 所有兵种、建筑、阵营、卡牌和经济数值由配置驱动。
4. 每个系统有单一职责，新增规则不再继续扩大 `GameManager`。
5. 同一套模拟核心支持真人操作、AI 对战、批量平衡测试和未来回放。
6. Cocos 场景只保留启动所需的 Canvas/Camera，游戏对象由表现层管理。

## 2. 当前基线

当前唯一核心脚本是 [GameManager.ts](../assets/scripts/GameManager.ts)。它已经包含可运行的灰盒循环，但存在以下架构问题：

- 配置常量、实体结构和系统逻辑全部写在同一文件。
- `G: any` 是唯一状态容器，没有稳定的数据契约。
- 游戏逻辑直接创建和销毁 Cocos 节点。
- UI 事件直接修改金币、建筑和 buff。
- AI、战斗、卡牌和胜负判定之间没有清晰边界。
- 运行时脚本挂在场景 Canvas 下的 Camera 节点，脚本还会再次创建 Canvas/Camera。

这些问题不通过一次性重写解决，按第 8 节的迁移顺序逐步拆出。

## 3. 目标模块结构

```text
assets/scripts/
  config/
    game-config.ts       # 全局参数、经济、时间、人口、地图
    faction-config.ts    # 三阵营修正和被动
    unit-config.ts       # 兵种模板、克制、赏金
    building-config.ts   # 建筑、升级、价格规则
    card-config.ts       # 卡牌定义、稀有度、触发波次
  core/
    types.ts             # 所有实体、枚举、命令、事件类型
    game-state.ts        # GameState 创建、重置、序列化
    random.ts             # 可注入随机源，支持测试和回放
    game-engine.ts       # 固定顺序推进一帧
    systems/
      economy-system.ts  # 工资、赏金、价格递增、反击工资
      wave-system.ts     # 全局波次和工厂计时
      spawn-system.ts    # 工厂出兵、人口上限、阵营被动
      combat-system.ts   # 索敌、克制、伤害、建筑攻击
      building-system.ts # 建造、升级、拆除、学院、光环塔
      ai-system.ts       # 简单/普通/困难决策
      card-system.ts     # 抽牌、暂停、效果、持续 buff
      victory-system.ts  # 水晶、决战时刻、胜负和星级
  presentation/
    game-view.ts         # 水晶、单位、建筑的节点池和位置同步
    hud-view.ts          # 顶部状态和建造栏
    panel-controller.ts  # 开始、卡牌、结算、提示面板
    color-sprite-factory.ts # 当前灰盒纯色 Sprite 生成
  input/
    game-commands.ts     # UI/触控转成类型化命令
  GameManager.ts         # 生命周期编排和模块装配，目标控制在 150 行以内
```

文件名可以按实际拆分调整，但依赖方向必须保持：

```text
config → core/types
core/systems → core/game-state + config
core/game-engine → core/systems
presentation/input → core/game-engine 的公开 API
GameManager → 装配 core、presentation 和 Cocos 生命周期
```

`core` 不允许导入 `cc`。只有 `presentation` 和入口 `GameManager` 可以依赖 Cocos。

## 4. 核心数据模型

所有对象先定义 TypeScript 类型，再实现逻辑。禁止在新代码中引入无约束的 `any`。

### 4.1 GameState

```ts
interface GameState {
  phase: 'idle' | 'playing' | 'card-pause' | 'ended';
  time: number;
  wave: number;
  waveTimer: number;
  playerSide: Side;
  factions: Record<Side, FactionId>;
  difficulty: Difficulty;
  gold: Record<Side, number>;
  salaryTimer: Record<Side, number>;
  units: UnitState[];
  buildings: BuildingState[];
  towers: TowerState[];
  crystals: CrystalState[];
  buffs: BuffState[];
  cards: CardState;
  stats: MatchStats;
}

interface Position {
  x: number;
  y: number;
}
```

### 4.2 实体规则

- 每个实体都有稳定 `id`，表现层以 `id` 建立节点映射，不以数组下标绑定。
- `UnitState`、`BuildingState`、`TowerState`、`CrystalState` 只保存模拟需要的数据。
- 位置单位统一使用像素坐标；设计文档中的“格”在配置加载时转换。
- 伤害、死亡、赏金和事件由 `combat-system` 统一结算，其他系统不得私自改写击杀统计。
- buff 使用统一结构，明确 `source`、`side`、`stat`、`value`、`duration` 和叠加规则。

## 5. 游戏帧和命令流

每帧由 `GameEngine.step(dt)` 按固定顺序执行：

1. 处理外部命令（建造、升级、选卡、暂停/继续）。
2. 推进时间、工资和波次。
3. 处理工厂出兵和人口上限。
4. 处理 AI 决策并转成同样的建造命令。
5. 更新单位、建筑、塔和水晶战斗。
6. 结算死亡、赏金、拆厂和统计事件。
7. 应用/减少临时 buff。
8. 检查决战时刻和胜负。
9. 输出只读 `GameSnapshot` 给表现层。

UI 不直接改 `GameState`，只提交如下类型化命令：

```ts
type GameCommand =
  | { type: 'build'; building: BuildingId; position: Position }
  | { type: 'upgrade'; buildingId: string }
  | { type: 'choose-card'; cardId: CardId }
  | { type: 'select-faction'; faction: FactionId }
  | { type: 'select-difficulty'; difficulty: Difficulty }
  | { type: 'restart' };
```

## 6. 表现层约定

- `GameView` 只负责节点池、颜色/资源、位置、缩放、动画和销毁表现。
- `HUDView` 和 `PanelController` 只读取快照和发送命令。
- 灰盒阶段继续使用纯色 Sprite，但通过 `ColorSpriteFactory` 集中生成，后续可替换为 SpriteFrame。
- 不在每帧按数组长度创建/销毁节点；使用 `id → Node` 映射和对象池。
- 死亡表现、伤害跳字、屏幕震动等属于表现事件，不写入核心规则。
- 场景保留一个 Canvas 和一个正交 Camera；不要在业务脚本中重复创建 Canvas。

## 7. 配置和版本规则

配置从 TypeScript 常量迁移到 `assets/config/*.json`，由配置加载器校验后生成运行时配置。迁移完成前，旧常量只能作为临时兼容层。

每个配置对象必须包含 `id`、`version` 和必要字段。数值调整必须同时更新《02-数值设计表》和配置文件，并记录变更原因。

版本优先级：

1. 玩法规则：`DOCS/01-玩法设计总纲.md`
2. 数值规则：`DOCS/02-数值设计表.md`
3. 工程边界：本文档
4. 实施顺序和验收：`DOCS/03-开发落地路线图.md`

如果文档和代码冲突，以文档为目标，先在路线图中登记差异，再修改代码；不得用“代码当前能跑”替代规则验收。

## 8. 分阶段迁移

### A0：基线冻结

记录当前可运行行为、入口场景、设计分辨率和已知差异。建立最小启动冒烟检查。

### A1：类型和配置

先提取 `types.ts`、配置模块和 `createInitialState()`，保持现有行为不变。完成后删除新代码中的 `any`。

### A2：模拟核心

把 `gameStep`、单位更新、攻击、出兵、胜负判定移到 `core`。用纯数据测试验证同一输入产生同一结果。

### A3：系统补全

按路线图补齐经济、建筑升级、兵种克制、AI 三档、卡牌持续效果和决战时刻，并为每个系统添加测试。

### A4：表现层解耦

将运行时节点创建、UI 面板和输入事件移出 `GameManager`。入口只负责装配和生命周期。

### A5：性能和内容

接入对象池、SpriteFrame、动画、音效、资源分包和真机性能指标。

## 9. 测试策略

- 单元测试：工资、价格递增、伤害克制、出兵、人口上限、卡牌和胜负。
- 模拟测试：固定随机种子批量跑阵营对局，记录胜率、平均时长、水晶剩余和经济峰值。
- 集成冒烟：进入场景、开始游戏、建造、选卡、结算、再来一局。
- 视觉检查：桌面 1280x720、窄屏和低端机帧率；确认节点数量不随时间失控。

每个里程碑必须同时具备“代码完成、测试通过、文档状态更新”三项，才能标记完成。

## 10. 明确不纳入当前版本

实时 PVP、账号系统、排行榜、皮肤商城和复杂技能树不进入当前主线。它们只能在单机规则稳定、模拟核心可复用后另立里程碑。

## 11. 技术债务登记（v1.8 复查，2026-09-06）

分层骨架健康：`core/` 全目录零 `import 'cc'`（已验证），系统粒度小（economy 35 行 / wave 20 行），新增卡牌/系统不侵入老代码。债务集中在表现层与装配层，按偿还优先级登记如下。

### 债务 D1：GameManager 超重（优先级：高，下一个功能迭代前偿还）

- **现状**：`GameManager.ts` 1501 行，本文档 §3 目标为 ~150 行，超 10 倍。
- **成因**：生命周期 + 模块装配 + 事件路由 + 网格放置模式（`onBuildClick`/`snapToCell`/预览红绿反馈）+ 逐帧快照 diff（`detectEffects`/`prevUnits` 全家桶）持续堆积在同一类里。
- **偿还方案**：拆出两个纯逻辑模块——`input/build-placer.ts`（放置模式状态机）与 `presentation/effect-detector.ts`（快照 diff 检测），GameManager 回归"装配 + 路由"，预计可减 ~600 行。
- **风险**：低。纯搬移不改行为，浏览器实机 + vitest 双重验证手段齐全。
- **触发条件**：任何需要改动 GameManager 的新功能开工前（如局外循环主界面入口）。

### 债务 D2：panel-controller 面板拥挤（优先级：中，与图鉴功能一起偿还）

- **现状**：`panel-controller.ts` 1086 行，开始/阵营选择/卡牌三选一/升级/结算/卡牌详情/Toast 全部在一个类。
- **成因**：面板逐个累加，共享 `showToast` 等基础设施，一直没拆的动力。
- **偿还方案**：按面板拆文件（start-panel / card-panel / upgrade-panel / end-panel），Toast 独立成 `toast-service`。
- **触发条件**：卡牌图鉴/解锁进度界面（局外循环 UI）动工时顺路拆——该功能必然新增面板，正好一起理。

### 债务 D3：hud-view / game-view 体量偏大（优先级：低，暂缓）

- **现状**：`hud-view.ts` 833 行、`game-view.ts` 824 行。
- **评估**：两者职责边界仍清晰（HUD 只读状态、GameView 只做实体同步），内聚性尚可，行数大主要因程序动画与美术回退分支多。
- **决策**：暂不偿还。美术素材全面接入后（灰盒回退代码可能被精简），再评估是否仍需拆分，避免白干。

### 债务 D4：缺架构守卫测试（优先级：高，立即偿还）

- **现状**：分层规则（core 禁 cc、GameManager 行数上限）只存在于文档，无自动化约束，债务可能无声增长。
- **偿还方案**：新增 `tests/architecture.test.ts`：断言 `core/**` 无 `cc` 导入、`GameManager.ts` 行数 ≤ 上限（当前设 1500，逐次收紧）。
- **成本**：约 20 行测试，一次编写永久生效。
- **✅ 已偿还（2026-09-06，commit b1c0cc4）**：守卫测试 2 条用例上线并纳入全量回归；GameManager 剔除装饰性空行回到 1500 行基线。

### 债务 D5：兵种机制按类型硬编码（优先级：低，首个新机制兵种立项时偿还）

- **现状**：兵种数值属性（hp/atk/range/speed/赏金/出兵数）已全部数据驱动，但战斗**机制**存在 3 处 `type === 'xxx'` 硬编码分支——rush 首击倍率（含 `firstStrikeDone` 状态，combat-system）、siege 对建筑/水晶伤害 ×15、siege 对塔索敌半径特判。
- **成因**：机制先行、抽象滞后——5 兵种仅 2 种特殊机制时抽象收益低于成本。
- **影响**：新增"数值型变体兵种"（换数值/射程/定位）成本极低，`UnitType` 联合一加，TS exhaustive 检查强制补全全部 `Record<UnitType,...>` 配置点，core 逻辑零改动；但新增"新机制兵种"（治疗/召唤/光环/飞行）需在 combat-system 继续堆类型分支，堆多会重蹈 D1 膨胀覆辙。
- **偿还方案**：机制字段化——首击倍率、对建筑倍率、索敌规则下沉为 `UnitConfig` 可选字段（如 `firstStrikeMult?` / `vsBuildingMult?` / `detectByRange?`），combat-system 读字段而非判类型；后续新机制兵种按同一模式扩展字段。
- **触发条件**：首个带新机制的兵种立项时，先完成字段化再实现该兵种；纯数值变体兵种不受此约束。

### 偿还策略总述

不建议立即全量偿还：当前主线是玩法验证与数值平衡（中立卡池刚落地），重构打断节奏收益低。采用"触发式偿还"——守卫测试立即上（防利息滚动），其余债务绑定到必然触碰它们的功能迭代上顺路清偿。
