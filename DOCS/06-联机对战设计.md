## 1. 目标与范围

- **目标**：双玩家实时对战（1v1），沿用现有全部规则（阵营/兵种/建筑/卡牌/河道地图）
- **非目标**（本期不做）：观战、断线 AI 托管接管的复杂策略、段位赛季、好友系统、语音
- **范围**：微信/抖音小游戏 + H5 三端一致的 WebSocket 联机

## 2. 网络模型：帧同步（Lockstep）+ 瘦中继

### 2.1 选型理由

| 维度 | 帧同步（选） | 服务器权威 |
|---|---|---|
| 服务器成本 | 只转发命令，2C4G 扛起步全量 | 每局跑模拟，按局吃 CPU |
| 一致性实现 | 复用现有 core（两端同代码） | 服务端跑 core（也可行，但带宽高） |
| 回放 | **免费**（存命令流即可回放） | 需另存快照 |
| 反作弊 | 弱（客户端结算，靠哈希校验） | 强 |
| 输入频率适配 | 本游戏每分钟个位数命令，极契合 | 无优势 |

对抗作弊的补偿手段：服务器下发固定随机种子 + 双端定期状态哈希上报比对，不一致即判局无效。建造类策略游戏数值作弊收益有限（无走位微操），起步阶段够用。

### 2.2 协议概要

```text
C→S  join        { token, mode }            匹配
S→C  matched     { roomId, seed, oppFaction, yourSide, yourFaction }
S→C  start       { startAtTs }              双端同时进入
C→S  cmd         { frame, cmd }             GameCommand 原样（build/upgrade/research/choose-card）
S→C  frame       { frame, cmds: [...] }     该逻辑帧收到的全部命令，双端同序执行
C→S  hash        { frame, hash }            每 3s 一次状态哈希
S→C  hashdiff    { frame }                  哈希不一致 → 双端上报完整快照裁决
C/S  result      { winner, stats }          服务器汇总双方结算，以哈希一致为前提
S→C  reconnect   { frame, cmds[], snapshot? } 断线重连：重放命令流（超时则快照）
```

关键点：
- **逻辑帧 100ms（10 帧/秒）**，渲染仍 60fps，本地命令即时预执行、远端命令到帧生效（本游戏输入低频，预执行几乎无感知差异）
- 命令带逻辑帧号，服务器按帧聚合广播，**双端同序执行**是确定性的全部要求
- 服务器只做三件事：房间/匹配、命令转发与定序、哈希比对

### 2.3 同步安全线（必须先完成的改造）

| # | 事项 | 现状 | 改造 |
|---|---|---|---|
| S1 | 固定逻辑步长 | `engine.step(渲染dt)` | GameManager 加累加器，逻辑帧固定 1/30s（本地）/ 锁步 100ms（联机） |
| S2 | core 随机源全量收口 | bloom 树人位置用了 `Math.random()` | 改走注入的 RandomSource |
| S3 | 逐帧状态哈希 | determinism.test 只比终态 | 序列化核心字段（time/wave/gold/units 位置血量/nextId…）做稳定哈希，测试每 N 帧比对 |
| S4 | 命令对等 | 卡牌 27 张效果写死 `state.buffs.red`；出兵/工资按 side 已对等 | 卡牌效果按执行方 side 生效（含 AI 选卡策略） |
| S5 | 帧内顺序审计 | stepEconomy 红后蓝、stepCombat 按 units 数组序 | 数组序受实体 id 稳定排序约束，两端一致即可（当前 nextId 递增已保证） |
| S6 | 卡池双端一致（局外解锁前置约束） | drawOffers 联机取双方阵营卡池并集，保证双端 offers 相同 | 引入局外解锁系统后，联机对局卡池不受解锁进度影响（统一全量/赛季池），解锁过滤仅单机生效；任何卡池过滤必须双端结果一致，否则选卡命令在对端 offers 中失配 → desync（设计约束见 01-玩法设计总纲 §10.6） |

## 3. 系统架构

```text
微信/抖音/H5 客户端（现有 presentation + core）
        │ wss (帧同步协议)
        ▼
Node 联机服务（docker: node:20-alpine）
  ├─ gateway     ws 连接/心跳/鉴权（平台 openid 换 token）
  ├─ match       匹配队列（Redis）
  ├─ room        房间生命周期：start/frame 聚合广播/hash 比对/result/超时
  └─ replay      命令流落对象存储（异步，失败不阻塞对局）
        │
  ┌───┴────┐
Redis      PostgreSQL
匹配队列/    对局记录/
房间状态/    玩家档案/
排行榜       战绩统计
```

单进程起步（room 数 < 千级无压力），后续按 CPU 垂直扩或 room 分片水平扩，协议不变。

## 4. 云资源清单（生产）与本地 Docker 对应

| 生产资源 | 用途 | 起步规格 | 本地 Docker 替代 |
|---|---|---|---|
| 域名 + ICP 备案 | ws 服务域名 | 1 个 | ⚠️ 备案 2~4 周，**现在启动** |
| 云服务器 | 联机服务 | 2C4G | 本机 docker compose |
| WSS 证书 | 平台强制 wss | 免费 DV | 本地 mkcert/自签 |
| Redis | 匹配/房间在线态/排行榜 | 1GB | `redis:7-alpine` |
| PostgreSQL | 对局/玩家/战绩 | 最小规格 | `postgres:16-alpine`（本机已有同版本经验） |
| 对象存储+CDN | 回放文件/资源分发 | 按量 | 本地 volume 目录 |

> 本地阶段不依赖任何云资源：**docker compose 一键起全套**（见 §5）。备案是唯一需要立即启动、又无法本地替代的事项。

## 5. 本地开发环境（docker compose）

```yaml
# docker-compose.yml（联机开发环境，置于 server/ 目录）
services:
  game-server:
    build: .                    # Node 20 + ws + redis/pg 客户端
    ports: ["8100:8100"]
    environment:
      REDIS_URL: redis://redis:6379
      DATABASE_URL: postgres://game:game@postgres:5432/game
    depends_on: [redis, postgres]
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
  postgres:
    image: postgres:16-alpine
    environment: { POSTGRES_USER: game, POSTGRES_PASSWORD: game, POSTGRES_DB: game }
    ports: ["55433:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
volumes: { pgdata: {} }
```

> 注意：本机已有 55432 端口的 postgres 容器（particle-card-postgres），联机的映射到 **55433** 避免冲突。

## 6. 服务端技术栈与仓库结构

- **运行时**：Node 20 + TypeScript（与前端同语言，core 代码**直接复用**——把 `assets/scripts/core` 与 `config` 通过 workspace/软链共享给服务端，服务器跑哈希校验与断线重连裁决）
- **ws 库**：`ws`（成熟、无框架绑定）
- **持久化**：`ioredis` + `postgres`（pg）+ 轻量 SQL 迁移脚本
- **部署**：Dockerfile（node:20-alpine，多阶段构建）→ compose / 后续 K8s 无关

```text
server/
  src/
    index.ts        # 启动/生命周期
    gateway.ts      # ws 连接、鉴权、心跳
    match.ts        # 匹配队列
    room.ts         # 房间状态机（核心）
    protocol.ts     # 消息类型（与客户端共享）
    db.ts           # pg 访问
    redis.ts        # redis 访问
  core -> 软链/复用 assets/scripts/{core,config}
  docker-compose.yml
  Dockerfile
```

## 7. 客户端改造点

1. **NetworkClient**（presentation 同级）：连接/心跳/重连退避，命令上行，帧下行
2. **GameEngine 输入缓冲**：本地命令即时入队 + 远端命令按帧注入；锁步未就绪时逻辑帧等待（UI 显示"等待对手"）
3. **GameManager**：固定步长累加器（S1）；联机模式下按 network 时钟驱动 step
4. **卡牌双端化**（S4）：AI 对手在联机模式下不存在，卡牌改按 `state.playerSide` 的真实双端语义（此改动同时兑现"AI 也抽卡"的单机选项）
5. **UI**：匹配页/对手信息/断线重连提示/结算双端一致校验

## 8. 节奏与里程碑（建议）

| 阶段 | 内容 | 量级 |
|---|---|---|
| P0（先行，可与单机并行） | S1 固定步长 + S2 随机收口 + S3 哈希测试（对单机亦有益，先行合入） | 2~3 天 |
| P1 | server 骨架：compose 起 redis/pg、gateway/match/room 跑通最小对局（本机双开浏览器验证） | 1~2 周 |
| P2 | 断线重连/哈希校验/结算入库/回放落盘 | 1~2 周 |
| P3 | 卡牌双端化（S4）+ 联机 UI（匹配/断线/结算） | 1 周 |
| P4 | 压测（room 数/断连率）+ 云资源上生产 | 1 周 |

**总计约 5~7 周**（单人、含测试）。P0 与 P1 可在单机上线前并行启动，P2 起建议等单机真人数据回流后立项。

## 9. 风险与未决项

| 风险 | 对策 |
|---|---|
| 微信/抖音 socket 合法域名需已备案 + wss | 备案立即启动；本地/内网测试不受限 |
| 帧同步隐性不同步（浮点/遍历序/随机） | S2/S3/S5 全量收口 + CI 跑长局哈希对比 |
| 平台托管联机引擎（MGOBE 类）下架传闻 | 不绑定平台引擎，自建 ws |
| 玩家存量不足匹配慢 | 起步支持"好友房/房间码"，排位匹配做二级开关 |
| 对局中途玩家退出 | 退出方判负（15 秒宽限），对局记录标注 |
